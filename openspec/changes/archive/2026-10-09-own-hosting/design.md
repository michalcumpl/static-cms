# Design

## Context

See proposal.md for why. Today `apps/admin/src/lib/server/publishing/` publishes through one
`PublishTarget` (`target.ts`), implemented by `netlify.ts`. It gets that target from the
workspace's connection (`publishTarget(db, workspaceId)` in `connection.ts`). Every caller goes
through the workspace: `publish.ts` (publish and restore), `domains.ts`, and
`project-deletion.ts`. `project_hosting` has one row per published project, with `provider`
(`"netlify"`), `siteId`, `siteName`, `defaultUrl`, the domain and its state, and `livePublishId`.
The export already writes `404.html` and a Netlify-format `_redirects` file (`from to 301` per
line) at the root of every publish.

The AWS facts that shape the design were checked against the CloudFront documentation:

- **CloudFront Functions:** code is at most 10 KB, with one key-value store (KVS) per function.
- **KVS:** keys up to 512 B, values up to 1 KB, at most 5 MB per store, and at most 50 keys per
  update request. Writes need the store's current ETag.
- **Multi-tenant distributions:** at most 10,000 tenants per account. Lambda@Edge and custom
  error responses are not on the list of unsupported features. Minimum, default and maximum TTL
  can't be set on the distribution, only through a cache policy.
- **Error responses:** a viewer-request function does **not** run when CloudFront fetches a
  custom error page. Viewer-response functions don't run for origin statuses of 400 and above.
  Only a Lambda@Edge origin-response function sees an S3 miss and can answer it with a body of
  its choice.

## Goals / Non-Goals

**Goals:**
- One storage-and-edge interface (`HostingBackend`) that the Webmio adapter uses. The AWS
  implementation is thin, and a fake implements the same interface for vitest and Playwright.
- The routing logic lives once, in `packages/edge`. The same code runs at the edge, in the fake,
  and in unit tests.
- Edge caches never need an invalidation: a publish's files are immutable under their own
  prefix.

**Non-Goals:**
- Concurrent publishes across several admin servers. The single in-process queue in `publish.ts`
  stays.
- Making KVS writes transactional across keys. The design needs just one key written per switch.
- Per-tenant WAF, geo-restrictions or logging.

## Decisions

### 1. Bucket layout: a website folder, with a folder per publish

```
sites/<siteId>/<deployId>/index.html
sites/<siteId>/<deployId>/kontakt/index.html
sites/<siteId>/<deployId>/404.html
sites/<siteId>/<deployId>/_redirects
sites/<siteId>/<deployId>.manifest.json   ← { path: sha256 } of that publish
```

- `siteId` is a new id per website (`ws_…`), not the project id. A project restored after
  deletion gets a clean folder, and the old one can be deleted without races.
- `deployId` is generated by the adapter (`dp_…`) and stored in `publishes.deploy_id`, as Netlify's
  is today.
- The bucket is private. CloudFront reads it through origin access control (OAC).

*Alternative:* content-addressed objects (`objects/<sha>`) shared between publishes, with a
manifest per publish. This saves storage, but the router would need a path → hash lookup per
request, which doesn't fit in the KVS. Copying unchanged files inside S3 is free of transfer and
fast enough for sites of tens of megabytes.

### 2. KVS keys: hostname → website, website → live publish

| Key | Value | Written when |
| --- | --- | --- |
| `h:<hostname>` | `<siteId>` or `<siteId> <redirectHost>` | site created, domain connected, ready or disconnected, site deleted |
| `s:<siteId>` | `<deployId>` | every publish and rollback |

- **Atomic switch:** publishing and rollback write just `s:<siteId>`, so a website's free address
  and custom domain switch together.
- **Redirect to the custom domain:** the free address's `h:` entry carries the custom domain's
  hostname once it is ready (`ws_x www.pekarna.cz`). The custom domain's own entry never has one.
- **Budget:** about 80 B per entry and at most 3 entries per website (free address, served
  domain, live publish). That is about 60,000 websites in 5 MB, more than the 10,000-tenant quota
  allows.
- **Writes** go through a small helper. It reads the ETag (`DescribeKeyValueStore`), sends
  `UpdateKeys` with puts and deletes, and retries once on `ConflictException`. Domain checks can
  run beside a publish.

*Alternative:* one `h:` entry per hostname that holds the live deploy id. A rollback would then
write two keys, and the two hostnames could disagree for a moment. Rejected.

*Alternative:* redirects as KVS entries (`r:<deployId>:<path>`), as the proposal first said.
Ten kept publishes × tens of redirects × hundreds of websites exhaust the 5 MB store. Rollback
would also need to write many keys, so it wouldn't be atomic. Rejected for decision 4.

### 3. The viewer-request function (`packages/edge/src/router.js`)

It runs for every request on the distribution's single cache behavior:

1. Lowercase the `host` header and look up `h:<host>`. If it is missing, return a small "No
   website here" page with status 404. The body is inline in the function and isn't cached.
2. If the entry has a redirect host, return a 301 to `https://<redirectHost><uri>`, with the
   query string.
3. Look up `s:<siteId>`. If it is missing (never published, or deleted), return "No website
   here".
4. Normalise the path:
   - Decode it once.
   - Reject `..` and `.` segments, backslashes, NUL bytes and encoded slashes with "No website
     here". This decides the "Escaping the publish" scenario.
   - An address without a trailing slash and without an extension gets a 301 to `<uri>/`.
   - An address ending in `/` gets `index.html` appended.
5. Rewrite the URI to `/sites/<siteId>/<deployId><path>`, re-encoded, and drop the query string.

- **Cache key:** the rewritten URI. Because the deploy id is part of it, cached files of an old
  publish are never served after a switch.
- **HTTP:** the viewer protocol policy `redirect-to-https` covers the HTTP → HTTPS redirect.
- **Packaging:** the router is written as `route(request, lookup)` with no imports, so Node tests
  can call it. A build step in `packages/edge` produces `dist/viewer-request.js` for the
  CloudFront Functions runtime 2.0: it strips the `export` keywords and appends the handler that
  binds `lookup` to `cf.kvs()`. A test checks that the bundle stays under 10 KB.

### 4. Not found and redirects: a Lambda@Edge origin-response function

`packages/edge/src/not-found.js` exports `resolveMissing({ uri, read })`. The handler runs only
when S3 answers 403 or 404 (no `s3:ListBucket`, so a missing key is a 403):

- It derives `sites/<siteId>/<deployId>/` from the rewritten URI.
- It reads that publish's `_redirects`, cached in memory per deploy id. If the original path
  matches, with or without its trailing slash and `index.html`, it returns a 301 to the target.
- Otherwise it returns that publish's `404.html` with status 404 and `text/html; charset=utf-8`.
  If `404.html` is missing too, it returns a plain "Page not found".
- Responses carry `cache-control: public, max-age=0, must-revalidate`. The cache policy keeps
  them at the edge like any other file of the publish (decision 6).

**Configuration:** Lambda@Edge has no environment variables. The Pulumi program writes the bucket
name and region into the bundle at deploy time, as it does for the function. The function runs
in `us-east-1` with a role that may only `s3:GetObject` under `sites/*`.

*Alternative:* a CloudFront custom error response (403 → `/404.html`). The error-page fetch
skips the viewer function, so it can't find the website's publish, and it can't apply redirects.
Rejected.

*Alternative:* a list of each publish's paths in the KVS, so the router can decide. The list
doesn't fit in a 1 KB value. Rejected.

### 5. Uploads: copy what the previous publish had, upload the rest

`deploy(siteId, files)` in `webmio.ts`:

1. Hash every file (SHA-256).
2. Read the manifest of the website's live deploy, if there is one.
3. For each file, `CopyObject` from the live deploy when the hash matches. Otherwise
   `PutObject` with its content type and cache control (decision 6). Eight run at a time.
4. Write the new manifest last, then write `s:<siteId>` (decision 2).
5. On any failure, delete the new deploy's prefix and rethrow as a `PublishError`, so a failed
   publish leaves no files ("Keeping publishes").

- **ETags:** `CopyObject` keeps the source's ETag for single-part objects, so a browser
  revalidating an unchanged file still gets a 304 after a new publish.
- **Hosting-only files:** `_redirects` is uploaded like any other file, for the not-found
  handler. The router rewrites a request for `/_redirects` to a key that never exists, so
  visitors get the website's 404 page and never the file.

### 6. Caching

- **Edge:** one custom cache policy with minimum, default and maximum TTL of one year and no
  query strings, headers or cookies in the key. This is safe because each cache key includes the
  deploy id and is immutable.
- **Browsers:** they get the object's own `Cache-Control`, set at upload:
  - `public, max-age=0, must-revalidate` for `.html`, `.css`, `.js`, `.xml`, `.txt`,
    `.webmanifest`, `.json`;
  - `public, max-age=86400` for images and fonts.

  This matches the spec: pages and assets are revalidated on every load, and images and fonts are
  kept for up to a day. Asset file names have no content hash, so a longer browser cache would
  serve a stale stylesheet after a publish.
- **Content types:** a map in `packages/edge/src/content-types.js`, shared by the upload and the
  fake. Text types get `; charset=utf-8`, and unknown extensions get
  `application/octet-stream`.

### 7. Custom domains: one distribution tenant per website with a domain

- **Free addresses:** one tenant, `webmio-sites`, with the alias `*.<sitesDomain>` and an ACM
  wildcard certificate. It is created by Pulumi.
- **Connecting a domain:** writes `h:<servedHost>` and tries to create a tenant named after the
  site id, with the served hostname as its only alias and
  `ManagedCertificateRequest { ValidationTokenHost: "cloudfront" }`.
  - The served hostname is `www.<domain>` for a bare domain, and the domain itself otherwise.
    `isBareDomain` stays as it is.
  - CloudFront creates a tenant only for a domain whose DNS already leads to it ("Could not
    verify Domain Name ownership", found in the `dev` stack). A chain through the website's
    CNAME target is enough, and no `_cf-challenge` TXT record is needed. So while the member
    hasn't set DNS yet, no tenant is created and `domain_tenant_id` stays empty; the domain
    check creates it once DNS points at the target.
  - `CNAMEAlreadyExists` (or a similar conflict) maps to a new `PublishError` kind,
    `"domain-in-use"`, for the "Domain used elsewhere" scenario. When CloudFront reports it on
    connecting, the domain is refused; when it reports it only once DNS leads to us, the check
    answers with the same message.
  - The tenant asks ACM for its certificate as the caller, so the admin needs
    `acm:RequestCertificate` and `acm:DescribeCertificate`.
- **Checking the domain:**
  - DNS: does `resolveCname(servedHost)` name this website's target,
    `<siteName>.<cnameDomain>`, exactly? A CNAME at the connection group's endpoint or at another
    website's target doesn't count, so the page keeps showing the record to set. The served
    hostname is never a bare domain, so no DNS host flattens its CNAME.
  - Certificate: the adapter reads `GetManagedCertificateDetails`. When the certificate request
    has failed or expired (DNS was set too late), it requests a new one and the state stays
    "issuing the certificate". An issued certificate serves nothing until the tenant uses it:
    the adapter sets it as the tenant's certificate (as the console's last step does), which
    makes the domain active. Only then is the domain "ready". In the `dev` stack the
    certificate was issued within a minute of DNS pointing at us.
- **Becoming ready / disconnecting:** when the state becomes `ready`, `domains.ts` calls the
  target's new `setRedirectHost(site, servedHost)`, which rewrites the free address's `h:`
  entry. When it stops being ready, the redirect is removed. Disconnecting deletes the tenant,
  the `h:<servedHost>` entry, and the redirect.
- **Releasing a domain:** CloudFront deletes a tenant only once it is disabled, and disabling
  takes minutes to reach every edge. Disconnecting a domain or deleting a website therefore
  disables the tenant and tries to delete it; if CloudFront isn't ready, the disabled tenant
  stays. It serves nothing, because its `h:` entry is gone. When the domain is connected again
  (to any website) before then, `CNAMEAlreadyExists` names a tenant of our own distribution,
  and the backend takes it over: it re-enables the tenant and requests a new certificate. So the
  domain can be connected again right away. Disabled tenants left behind cost $0.01 a month
  each; deleting them later is a job for `scheduled-jobs`.
- **DNS: a CNAME target per website.** Each website's target is `<siteName>.<cnameDomain>`
  (`pekarna-u-lipy.sites.webmio.net`). It is derived from the free name, which never changes, so
  it needs no column.
  - Pulumi creates one wildcard Route 53 record, `*.sites.<netDomain>`, as a CNAME to the
    connection group's routing endpoint. Publishing creates no DNS records.
  - To move one website later (to a connection group with Anycast static IPs for its bare domain,
    another tier, or a new distribution), we add a specific record for its target. That record
    takes precedence over the wildcard, and the owner's DNS stays as it is.
  - Every target resolves, even one that isn't a website's (yet). That's harmless: no tenant
    serves the `sites.<netDomain>` names themselves, so CloudFront refuses requests to them, and
    routing to a website goes only by the customer's hostname.

*Alternative:* one shared target, `sites.webmio.net`, for every website. It is simpler to
explain, but moving a single website would mean asking its owner to change DNS, and the check
couldn't tell whether a domain points at this website or at another one. Rejected.

*Alternative:* one tenant per website, also for its free address. This uses the tenant quota for
websites without a domain, and the free address would wait for a certificate. Rejected.

### 8. Choosing the target per project

`connection.ts` gets `targetFor(db, projectId, options)`, which returns the target and its
provider:

1. A `project_hosting` row with `provider = "webmio"` uses the Webmio target.
2. A row with `provider = "netlify"` uses the workspace's Netlify connection, or none.
3. With no row, the Webmio target when `webmioHostingConfig(env)` is set, and the Netlify
   connection otherwise.

- **Callers:** `startPublish`, `restorePublish`, `connectDomain`, `disconnectDomain`,
  `checkDomain` and `deleteProject` call it instead of `publishTarget(db, workspaceId)`.
- **Options:** `NetlifyEnv` becomes `HostingEnv`, which adds `webmio?: HostingBackend` so tests
  can inject the fake.
- **Not connected:** the `not-connected` result now happens only for rule 2, or rule 3 without
  Webmio hosting.
- **The publishing endpoint:** the project's publishing endpoint replaces `connected` with
  `canPublish` and `provider`, so the Publish, Website and Overview pages need no Webmio-specific
  branches beyond the domain instructions.

`webmioHostingConfig(env)` reads these variables. It returns `undefined` unless the bucket, the
KVS ARN, the distribution id and the connection group id are all set:

- `WEBMIO_HOSTING_BUCKET`
- `WEBMIO_HOSTING_KVS_ARN`
- `WEBMIO_HOSTING_DISTRIBUTION_ID`
- `WEBMIO_HOSTING_CONNECTION_GROUP_ID`
- `WEBMIO_SITES_DOMAIN` (default `webmio.site`)
- `WEBMIO_CNAME_DOMAIN` (default `sites.webmio.net`): websites' CNAME targets are
  `<name>.<this>`
- `AWS_REGION`

Credentials come from the SDK's default chain and never pass through our code.

### 9. `PublishTarget` grows, and stays provider-neutral

- **New and optional:**
  - `setRedirectHost?(siteId, host | null)`
  - `prune?(siteId, keepDeployIds)`
  - `servedHost?(domain)`, which returns the hostname that is served for a domain.
- **`dnsRecords(domain, siteName)`** becomes per provider: the Netlify records as today, and for
  Webmio one CNAME plus a `forward: "https://www.<domain>"` instruction for a bare domain. The
  Domain page renders that instruction.
- **`siteAddress(hosting)`** uses `servedHost` for the address of a ready domain.
- **`PublishErrorKind`** gains `"domain-in-use"`.

Netlify ignores the optional methods. Its rollback keeps working for every publish, as today.

### 10. Free names and retention live in the database

- **Free names:** `freeSiteName(db, projectName)` slugifies the name: NFKD, diacritics removed,
  `[a-z0-9]+` joined by `-`, at most 40 characters, `web` if empty. It skips names in the
  reserved list (`www`, `api`, `admin`, `app`, `mail`, `sites`, `webmio`, `status`, `help`,
  `docs`, `blog`, `static`, `cdn`) and names already in `project_hosting.site_name`, appending
  `-2`, `-3`, ….
  - A new unique index on `project_hosting(provider, site_name)` turns a race into a retried
    insert.
  - `createSite` in the Webmio adapter refuses a name whose `h:` entry exists, mapped to
    `name-taken`. Deleted websites free their names.
- **Retention:** after a successful Webmio publish, `publish.ts` computes the kept deploy ids:
  the 10 most recent `ready` publishes plus the live one. It calls `prune(siteId, kept)`, which
  deletes every other deploy prefix and manifest. Rollback runs no prune.
  - A new column `publishes.files_deleted_at` is set for pruned publishes.
  - `publishingState` exposes `restorable` per publish: `ready`, has a deploy id, and no
    `files_deleted_at`.
  - `restorePublish` refuses a non-restorable publish with `cantRestore`.

### 11. Data model

One migration (`0002_own_hosting.sql`):

- `project_hosting.domain_tenant_id` (text, null): the CloudFront tenant of the website's
  domain.
- `publishes.files_deleted_at` (integer timestamp, null).
- A unique index on `project_hosting(provider, site_name)`.

`provider` is a Drizzle text enum without a CHECK constraint, so adding `"webmio"` changes no
SQL. For Webmio rows, `account_slug` holds `"webmio"`.

### 12. The fake, for vitest and Playwright

`webmio-fake.ts` implements `HostingBackend` on a directory: objects are files, and the KVS and
the tenants are JSON files. Tests can set a tenant's certificate state, or reject an alias as
used elsewhere.

`e2e/fake-webmio-server.ts` serves that directory over HTTP on a port. It calls the same
`route()` and `resolveMissing()` from `packages/edge`, with the hostname taken from
`<name>.localhost`. Playwright can open a published website and check rollback, redirects and
the 404 page.

The e2e environment sets `WEBMIO_HOSTING_FAKE_DIR`, which makes `targetFor` use the fake backend
instead of AWS. That variable is honoured only when `NODE_ENV !== "production"`. The existing
Netlify e2e flows move to vitest, which already covers them with `fake-netlify.ts`, except one
that publishes in a workspace connected to Netlify and stays on Netlify.

### 13. Infrastructure: Pulumi in `infra/`

`infra/` is a workspace package with `Pulumi.yaml`, `Pulumi.dev.yaml` and `Pulumi.prod.yaml`.
Each stack's config has `sitesDomain`, `netDomain` and `region`. The program creates:

- **The bucket:** private, versioning off, and a lifecycle rule that aborts incomplete multipart
  uploads. Its policy lets CloudFront read through OAC, and the Lambda role read too.
- **The edge code:** the CloudFront Function from `packages/edge/dist/viewer-request.js`, the
  KVS, and the Lambda@Edge function in `us-east-1` (a second provider) with its role.
- **The cache policy, and the multi-tenant distribution:**
  - one S3 origin, one behavior with `redirect-to-https`, both functions, and the cache policy;
  - the `webmio-sites` tenant;
  - the default connection group.
- **DNS:** Route 53 hosted zones for `sitesDomain` and `netDomain`, with wildcard records for
  `*.<sitesDomain>` and `*.sites.<netDomain>` pointing at the connection group (decision 7). Also the ACM
  wildcard certificate for `*.<sitesDomain>`, validated by DNS.
- **The admin's access:** an IAM user `webmio-admin-<stack>`, with an access key as a secret
  output. Its policy allows:
  - S3 get, put, copy and delete, and list on the `sites/` prefix;
  - `cloudfront-keyvaluestore:*Key*` and `DescribeKeyValueStore` on the KVS;
  - creating, getting, updating and deleting distribution tenants, and getting managed
    certificate details, on the distribution;
  - requesting and describing ACM certificates, for the tenants' managed certificates.
- **Outputs:** every `WEBMIO_*` variable and `AWS_REGION`.

The operator's steps are documented in `infra/README.md`: create the account, deploy, delegate
the zones, set the admin's environment.

The multi-tenant resources need a current `@pulumi/aws`. If a resource is missing there, the
program uses `@pulumi/aws-native` (Cloud Control) for that one resource. The first task checks
this.

## Risks / Trade-offs

- **[Lambda@Edge on a multi-tenant distribution]** → Confirmed by the spike in the `dev` stack
  (2026-10-09): the publish's 404 page and redirects are served. A Lambda@Edge response must
  change the origin's response in place; replacing its headers drops the read-only `Via` and
  `Transfer-Encoding`, and CloudFront answers 502.
- **[Wildcard alias on a tenant]** → Confirmed by the spike: the `*.dev.webmio.site` tenant
  serves every free address.
- **[KVS propagation takes seconds, not milliseconds]** → The spec allows "within a minute"; the
  `dev` stack measured 21 to 40 seconds from the write to the new deploy, and a new website's first publish took up to a minute to show. A publish is marked `ready` after
  the KVS write is accepted, not after it reaches every edge.
- **[A Lambda@Edge answer is cached for as long as its publish]** → A wrong redirect or 404
  page stays at the edge until the website publishes again. The handler is unit-tested as a
  bundle, so it is verified before it is deployed.
- **[The managed certificate request expires if DNS is set late]** → `checkDomain` requests a
  new certificate when the old request failed (decision 7), so the member only has to check
  again.
- **[S3 copy and put calls for large sites]** → A site of a few hundred files publishes in
  seconds, eight calls at a time. Only changed files are uploaded, so later publishes are faster.
- **[Deleted name reused by another customer]** → Cached files of the old website sit under its
  own `siteId`, which no hostname maps to any more, so a new owner of the name never sees them.
- **[A Lambda@Edge cold start delays the first 404 or redirect]** → It runs only on cache misses
  of missing addresses, and its responses are cached per publish.
- **[The admin's long-lived access key]** → It is stored only in the server's environment, its
  permissions are scoped to the hosting resources, and it is rotated with
  `pulumi up --replace`. Moving the admin to AWS (`admin-on-aws`) replaces it with a role.
- **[A single KVS shared by `dev` and `prod`]** → No: every stack has its own KVS, distribution
  and bucket.

## Migration Plan

1. Merge with Webmio hosting unconfigured. Behaviour is unchanged: publishing goes to Netlify,
   and only the migration runs.
2. Deploy the `prod` stack, delegate `webmio.site` and `webmio.net` to Route 53, and wait for the
   wildcard certificate.
3. Set the `WEBMIO_*` variables and the access key on the server, and restart. New and restored
   websites publish to Webmio hosting, and websites on Netlify stay there.
4. **Rollback:** unset `WEBMIO_HOSTING_BUCKET` and restart. New publishes go to Netlify again.
   Websites already on Webmio hosting keep serving from the edge, but can't be published until
   the variable is set again (`targetFor` rule 1 finds no backend and refuses with the not set up
   message).
