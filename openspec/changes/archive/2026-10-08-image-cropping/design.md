# Design

## Context

See proposal.md for the motivation. The code as it stands:

- **Media storage** (`apps/admin/src/lib/server/media.ts`). `uploadImage` hashes the bytes,
  returns an existing row with the same `sha256`, and otherwise `inspect`s and `storeImage`s:
  `sharp(...).rotate()` gives a metadata-free original in `originals/<key>.<ext>` and the WebP
  ladder `<key>-<w>.webp`. Uploads run one at a time (`serially`). `newKey` makes
  `slug(name)-<sha256 prefix>`. `derivedSource` already falls back to the largest variant for
  images registered before the library.
- **`media` table** (`db/schema.ts`): `projectId, key, sha256, originalName, format, width,
  height, bytes, createdAt, createdBy, removedAt`. It is unique on `(projectId, sha256)`. There
  is one flattened migration, `drizzle/0000_initial.sql`.
- **Document.** `image { src, alt, decorative, width, height }`, all owners hold it as a
  `node_array` of at most one image. The schema is at version 11 (`SCHEMA_VERSION` in
  `validate/domain.ts`, the default in `schema.ts`), and `migrateSite` upgrades one step at a
  time. Stored documents are upgraded on read (`upgrade-projects.ts` at startup).
- **Rendering.** `renderImage` in `packages/render/src/blocks.ts` is the only place that emits
  an `<img>` for a content image. Shapes come from the stylesheet: `object-fit: cover` with
  `aspect-ratio` 4:3 (gallery, card), 16:10 (project cover), 1:1 (portrait, testimonial photo),
  and the viewport for the full-photo hero and slides. Nothing sets `object-position` except the
  site logo. No page carries a `style` attribute today, and there is no CSP that forbids one.
- **Editor.** `MediaLibrary.svelte` is a `<dialog>` opened via `editor.openLibrary` from
  `image-slots.ts` (canvas, Image panel) and `form/FormImage.svelte` (people, testimonials,
  projects). `setImage` in `transforms.ts` replaces an image, and keeps the description only when
  the same key is chosen again.

## Goals / Non-Goals

**Goals:**
- An edit is just another library image. Rendering, export, publishing, icons, share files,
  the preview and cleanup see an ordinary media key.
- Edits are reproducible and lossless with respect to the source: always cut from the source's
  original, never from a crop.
- Upgraded documents render byte for byte as before (snapshot tests unchanged).

**Non-Goals:**
- Doing the crop in the browser and uploading the result. The server already holds the full
  original, and the browser would only re-encode a JPEG that the server re-encodes again.
- A third-party cropper widget.
- Pruning old crops that nothing uses. Cleanup already handles removed ones.

## Decisions

### 1. The edit is applied on the server, from the original

`POST /api/projects/<p>/media/<key>/edit` takes the body `{ turn: 0|90|180|270, crop: { x, y,
width, height } }` in pixels of the turned picture. `editImage(db, projectId, userId, key,
edit)` in `media.ts`:

1. Loads the row for `key`. If the row has a `sourceKey`, it switches to the source, so edits
   always start from the source. The client sends the frame relative to the source, which is
   what the library JSON gives it.
2. Validates: a known turn, integer rectangle inside the turned size, at least 64 × 64. A
   failure returns 400 `{ message }` (`server.media.cropOutside`, `server.media.cropTooSmall`).
   No turn plus a full rectangle returns the source row as is (200).
3. Reads the source's original (`originals/<key>.<ext>`, or the largest variant via
   `derivedSource`). It runs `sharp(bytes).rotate(turn).extract(rect)`, encodes in the source's
   format (WebP for legacy sources), and hashes the encoded bytes.
4. If a row with that `sha256` exists, it returns it (bringing it back if removed). Otherwise it
   stores the result through the same `storeImage` path, with `newKey(originalName of source,
   sha256)`, and inserts the row with `sourceKey` and `edit`. Files go first and the row last,
   as for uploads.

It runs inside `serially`, like uploads, for the same memory reason. sharp's encoders are
deterministic for the same input, options and version, so "same edit twice → same image" holds
through the hash. A sharp upgrade could make the hash differ, which would only produce a second
identical-looking crop.

- **Alternatives.** *Hash the edit parameters instead of the output.* That would need a separate
  key scheme, and the unique `sha256` index would no longer mean "same pixels". *Crop in the
  browser with canvas and upload.* That loses quality (a re-encode of a re-encode), can't use the
  original that is never served, and bypasses the 20 MB and 40 MP checks in odd ways.

### 2. Two nullable columns on `media`

`source_key text` and `edit text` (JSON `{ turn, crop }`), both null for uploads, generated by
drizzle-kit as migration `0001`. `toItem` and the library JSON gain `source?: { key, turn,
crop }`. A self-reference is not declared as a foreign key: keys are unique only per project,
and cleanup enforces the relation (decision 6).

### 3. Focal point as two integers on `image`, schema version 12

`focus_x` and `focus_y`, integers 0–100, default 50. `toVersion12` sets both to 50 on every
image node and bumps the version. Validation adds `invalid-focal-point` (category `site`). The
builder and fixtures write 50, 50 unless told otherwise.

- **Why per use:** the same photo shows as a 1:1 portrait and as a 16:10 cover. One point
  rarely suits both, and a library-level point would need copying into documents anyway, because
  rendering only sees the document.
- **Why integers, not floats:** they are stable in JSON diffs and version comparisons, and a 1%
  step is finer than anyone can see.

### 4. Rendering with a class and a per-page `<style>`

`renderImage` adds the class `focus-X-Y` when the point isn't 50, 50, and records it on the
render context (`useFocalPoint`, cleared by `startPage` along with the page's scripts).
`renderDocument` renders the header's logo first, then ends the head with one `<style>` holding
`.focus-X-Y{object-position:X% Y%}` for each class the page used, sorted. The values are
validated integers, so nothing needs escaping beyond the usual.

- **Why not a `style` attribute** (the first plan): html-validate's recommended rules, which
  every rendered page passes, forbid inline styles (`no-inline-style`), and a strict content
  security policy for our own hosting would need `'unsafe-hashes'` for them. A `<style>` element
  can be allowed by a hash computed at export. Chosen with the owner on 2026-10-08.
- **Alternatives.** *Rules in `assets/style.css`*: the stylesheet would depend on content as
  well as the theme, and on every language's document. *A class per possible value*: 10,201
  rules.

The editor's canvas (`nodes/Image.svelte`) sets `object-position` directly (the admin isn't
held to the site's rules) so that the canvas matches the site.

### 5. One crop dialog, three entry points

`CropDialog.svelte` is a `<dialog>` with `open({ key, source?, shape? }): Promise<ChosenImage |
undefined>`. It is mounted once next to `MediaLibrary` in the edit layout and in `SectionScreen`,
and exposed as `editor.openCrop`.

- **Display:** the source's largest variant is shown in a box with the turn applied by CSS. The
  frame is held in source pixels of the turned picture, and the view converts with one scale
  factor. The variant is used rather than the never-served original, so the pixel ratio is
  `source width / variant width`.
- **Frame logic** lives in a plain module `crop.ts`: `clampFrame`, `resizeFrame(handle, delta,
  shape)`, `fitShape`, `turnFrame` (rotating a frame with the picture), with unit tests. The
  component only maps pointer and key events onto it.
- **Accessibility:** the frame is a focusable element with `role="application"` and an
  `aria-label`, plus a live region announcing "x, y, width × height". The arrow keys move it by
  1% of the picture (Shift with the arrows resizes from the bottom-right corner). The turn and
  shape controls are ordinary buttons and a radio group.
- **Shapes per use:** `image-slots.ts` gains `shapeOf(ownerType, owner)`: gallery item →
  `4/3` only if the gallery's `image_fit` is `fill`, card → `4/3`, project → `16/10`, person
  and testimonial → `1/1`, page or site share image → `1200/630`, everything else free.

The entry points:
- **Library:** "Edit" next to "Remove" for the selected image. The result is put at the top of
  `images` and selected (the same code path as a finished upload).
- **Image panel and `FormImage`:** "Crop and rotate". A new transform `swapImage(tr, imageId,
  chosen)` changes `src`, `width` and `height`, resets the focal point and keeps
  `alt`/`decorative`. It is a separate function from `setImage`, whose rule "a different key
  starts undescribed" is right for choosing but wrong for cropping.

- **Alternatives.** *cropperjs*: it is about 40 KB, its v2 web components fight Svelte's
  styling, and it doesn't know our "shape per use". The frame maths is about 150 lines and
  testable on its own.

### 6. Cleanup keeps sources of kept images

`cleanupMedia` computes the set of keys it will delete (removed and unreferenced), then removes
from it every key that is the `source_key` of a row it keeps, until nothing changes. Sources are
only one level deep (decision 1), so one pass suffices, but the loop is cheap and safe.

### 7. Focal point control

`FocalPoint.svelte` shows the 480-pixel variant at the panel's width with a marker. It has
`role="slider"`-like keyboard handling on a focusable wrapper with `aria-valuetext` ("40 % from
the left, 30 % from the top"). It applies through `setImageFocus(tr, imageId, x, y)`: a click is
applied plainly, and key presses with `{ batch: true }`, as the alt text does. It is hidden for
`logo_item`, the site logo and the favicon (`object-fit: contain` or icons that fit the image
whole) and under `editor.sharedReadOnly` for collection items.

## Risks / Trade-offs

- **[Library clutter]** Every save adds an image, and owners may try several crops. → Identical
  edits deduplicate. The library shows the newest first, and Remove works as before. A "crops of
  this image" grouping can come later.
- **[A crop's description]** A crop may show less than the description says ("the team in front
  of the shop" → one face). → The description is kept because it is usually still right, and the
  Image panel stays open after cropping so the owner sees it.
- **[sharp version changes the hash]** → Only duplicates result. Nothing breaks.
- **[Large originals and memory]** A 40 MP rotate and extract needs memory like an upload. →
  Same serial queue and pixel limit.
- **[Share files ignore the focal point]** The `-share.jpg` is still cut from the centre. → The
  share-image slot offers a 1200:630 crop, which gives the exact framing.

## Migration Plan

1. Deploy: drizzle migration `0001` adds the two nullable columns. It runs on startup before
   any request.
2. Documents upgrade from version 11 to 12 when read, and are stored at their next save. Render
   output is unchanged for them.
3. Rollback: the old code ignores the new columns, but it would refuse version-12 documents
   (`unsupported-schema-version`). Rolling back after saves therefore needs a restore from
   Litestream, as for every format change so far.

## Changes made while building

- **The focal point is a class and a per-page `<style>`, not a `style` attribute** (decision 4,
  chosen with the owner on 2026-10-08): html-validate's `no-inline-style` refused the first plan.
- **A focal point that isn't a whole number** is a structural `invalid-value` error, like every
  whole-number property; `invalid-focal-point` covers values outside 0–100.
- **`GET …/media/<key>/edit`** describes one image for the crop dialog, removed from the library
  or not, and library items' `source` carries the source's width and height: a placed crop must
  reopen on its source even after either was removed. The dialog takes just a key and a shape
  (`editor.openCrop(key, shape)`) and fetches the rest.
- **Share image settings got "Crop and rotate"** as a fourth entry point; without it the 1200:630
  shape had nowhere to be used. A slot that gets a different image also resets its focal point.
- **The crop frame is a `<button>`** rather than a `role="application"` element, which Svelte's
  accessibility checks count as non-interactive; Enter and Space do nothing on it.
- **`storeImage` stores an edit's encoded bytes as the original** (`asOriginal`) instead of
  encoding them a second time.
- **The stage is sized from the dialog's width and the window's height**, not by measuring the
  stage itself, which made a ResizeObserver loop.
- **Tests:** the cropping e2e tests take their images out of the library afterwards, as other
  specs expect the demo picture alone under its name; the about-page tests address the image
  field's first picture, now that it shows the framed thumbnail and the focal point view.
- **The final check** (a crop and a focal point reaching the preview) ran on the e2e test
  project, not on the locally loaded example sites, so no local data was changed.
